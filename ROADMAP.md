## 1. Видение и границы проекта

Firefox Backup Manager остаётся небольшой Windows-утилитой для резервного копирования профилей Mozilla Firefox.

Главная ценность программы — не само создание файла `.7z`, а гарантированная и понятная пользователю цепочка:

1. Найти нужный профиль Firefox.
2. Получить согласованную копию его данных.
3. При необходимости зашифровать архив.
4. Проверить, что архив действительно создан и читается.
5. Сохранить предыдущие рабочие копии при любой ошибке.
6. Дать пользователю понятный способ проверить и восстановить данные.

### Принципы разработки

- **Сохранность данных важнее автоматизации.** При сомнении программа должна отказаться от операции, а не рисковать профилем или старыми копиями.
- **Fail closed.** Ошибка пароля, архивации, проверки или доступа не должна приводить к незашифрованной либо непроверенной копии.
- **Проверяемость.** Успех подтверждается кодом завершения архиватора и проверкой созданного архива, а не самим фактом запуска процесса.
- **Безопасное восстановление.** По умолчанию не перезаписывать действующий профиль Firefox.
- **Минимальная сложность.** Не добавлять облачные сервисы, телеметрию и тяжёлую инфраструктуру без реальной необходимости.
- **Совместимость сохраняется осознанно.** Любое изменение платформы или зависимостей сопровождается проверкой сборки и заявленных версий Windows.

### Что пока не входит в цель 1.0

- Поддержка Chrome, Edge и других браузеров.
- Поддержка Thunderbird и других приложений Mozilla.
- Облачная синхронизация и удалённое управление.
- Автоматическая миграция между разными версиями Firefox.
- Сложный интерфейс управления множеством устройств.

Эти направления можно рассматривать отдельно после стабильного релиза Firefox Backup Manager 1.0.

## 2. Зафиксированная исходная точка

План составлен по содержимому ветки `development` на базовом commit, указанном выше. На этой точке в репозитории находятся `compiler_code.cs`, `compile.bat`, README и две инструкции в каталоге `docs/`.

### Текущая реализация

- Однофайловое приложение C# с Windows Forms; манифест `asInvoker`, без запроса повышения прав.
- Сборка через системный компилятор C# из `compile.bat`.
- Обнаружение профилей через упрощённый разбор пользовательского `profiles.ini`.
- Внешний архиватор 7-Zip из стандартных каталогов Program Files.
- Конфигурация хранится в `%LOCALAPPDATA%\\Firefox Backup Manager\\PrivateConfig\\config.ini`.
- Сохранённый пароль защищается DPAPI `DataProtectionScope.CurrentUser`.
- Задача Планировщика запускается при входе текущего пользователя; тип входа `InteractiveToken`, уровень `LeastPrivilege`.
- Имя задачи содержит SID пользователя, поэтому разные учётные записи Windows не перезаписывают друг другу задачи.
- Запись резервных копий выполняется с правами вошедшего пользователя, не от SYSTEM.
- Ротация архивов по возрасту — 30 дней; ограничение размера журнала — 5 МБ.

### Оставшиеся проверяемые ограничения

- CI и ручной план должны подтвердить регистрацию пользовательской задачи, её реальный запуск после входа, а также работу в ограниченной учётной записи.
- Вход пользователя обязателен: задача не запускается до интерактивного входа.
- Резервирование/восстановление и запуск восстановленного профиля проверены вручную на реальной системе; CI остаётся синтетическим.
- Проверка работающего Firefox не блокирует его запуск атомарно.
- Текущая модель не даёт задаче прав SYSTEM, но не изолирует приложение от вредоносного процесса, уже работающего с правами того же пользователя.
- Поддержка сетевых/съёмных хранилищ и разные типы Windows-входа требуют ручной проверки.

## 4. Предлагаемая архитектурная последовательность

Не следует начинать с механического разбиения исходника на десяток файлов. Сначала нужно стабилизировать поведение и выделить проверяемые операции.

Рекомендуемый порядок:

1. Ввести единый объект результата резервирования и единый сценарий выполнения для первого и фонового запуска.
2. Выделить работу с 7-Zip: запуск, тайм-аут, ExitCode, вывод, тест и очистка временных файлов.
3. Выделить безопасную обработку конфигурации и пароля.
4. Выделить обнаружение профилей и проверку доступности выбранного пути.
5. Выделить планировщик и проверку фактического статуса задачи.
6. После появления автоматизируемых проверок разделить исходный файл на логические модули.

Так мы уменьшим риск большого рефакторинга, при котором одновременно меняются и структура, и поведение приложения.

## 5. Модель работы с GitHub

- `main` — стабильная ветка; прямые рабочие изменения в неё не вносятся.
- `development` — основная интеграционная ветка для подготовки следующего релиза.
- Для крупного или рискованного изменения можно создавать короткоживущую ветку от `development`, например `fix/backup-exit-code` или `feature/restore`.
- Изменения объединяются в `development` после проверки diff и критериев приёмки.
- Перенос в `main` — отдельное осознанное действие после проверки готовности релиза.
- Не выполнять force-push и не переписывать историю `main` без отдельной необходимости и согласования.
- Каждый коммит должен решать одну понятную задачу и иметь конкретное сообщение.

### Чек-лист перед объединением изменений

- [ ] Изменение соответствует задаче и не затрагивает несвязанные функции.
- [ ] Проверены ошибки и сценарии отказа.
- [ ] Не появились секреты, пароли или персональные данные в логах/коммитах.
- [ ] Обновлена документация, если изменилось поведение.
- [ ] Сборка выполнена на Windows либо явно отмечено, что она ещё не проверена.
- [ ] Проверены diff и список изменённых файлов.
- [ ] Критерии приёмки задачи выполнены.

**Выход спринта:** минимальный набор изменений, после которого программа больше не сообщает об успешном резервировании при очевидном сбое и не удаляет прежние копии после неудачной попытки.

## 7. Правило готовности

Задача не считается завершённой только потому, что исходный код изменён или компиляция прошла успешно.

Для каждой задачи должны быть указаны:

- что именно изменено;
- какой риск или дефект устранён;
- какие сценарии проверены;
- результат сборки;
- что осталось непроверенным;
- затронутые файлы и commit.

**Главный критерий готовности Firefox Backup Manager 1.0: пользователь может доверять не обещанию программы, а проверенному процессу создания и восстановления резервной копии.**
